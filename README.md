# Insurance claims intake: analysis & process redesign

**Where does a claims intake process lose time, and what should change?**

A synthetic-data case study combining process-mining analysis with a full business-analyst redesign package: a 5,000-claim event log, quantified bottleneck analysis, an as-is/to-be process redesign, and a simulated before/after comparison of the proposed changes.

> **All data in this repository is synthetic.** No real claims, customers, or company data appear anywhere in this repo. The event log is generated by `data/generate_claims_log.py`, committed alongside its output so the data is transparently synthetic rather than passed off as real.

## TL;DR

| | As-is | To-be (simulated) | Change |
|---|---|---|---|
| Average cycle time (blended) | 12.48 days | 9.03 days | **−27.6%** |
| Injury claims specifically | 20.63 days | 13.92 days | **−32.5%** |
| First-contact resolution | 82.8% | 94.3% | +11.5 pts |
| Documentation rework rate | 16.4% | ~5.0% | −11.4 pts |

The biggest lever turned out **not** to be the one that looked obvious going in. Four resource-constrained managers reviewing high-value claims looked like the headline bottleneck — it wasn't. The two largest cycle-time drivers were external waits: **medical records** (7.44-day average) and **additional documentation** (5.52-day average), together accounting for close to 40% of average cycle time. Manager review ranked third, and even there, the *average* wait was misleading — the median queue wait was 0 days; the real problem was a 4.91-day p90 tail from periodic load, not a permanent capacity shortfall. That distinction changed the recommendation from "hire a fifth manager" to "add a small overflow pool that only activates during congestion" — see the BRD for how that plays out.

## Approach

1. **Generate a realistic synthetic event log** — 5,000 claims, 57,781 events, across three claim types (Auto/Property/Injury) and four intake channels (Phone/Web/Mobile/Agent), with bottlenecks modeled as actual mechanisms (a resource-constrained queue for inspectors and managers, an external-wait documentation loop) rather than random noise layered onto a clean process.
2. **Quantify the as-is process** — cycle time by activity, rework loop frequency, handoff delay isolated from processing time, first-contact resolution, and cycle time by channel and claim type, using DuckDB as the SQL layer directly over the CSV.
3. **Turn the numbers into a redesign** — an as-is/to-be process map, a BRD with 9 functional requirements, 9 user stories with acceptance criteria, a requirements traceability matrix, and a UAT test plan, each traceable back to a specific quantified pain point.
4. **Validate the redesign by simulation** — rather than hand-estimating the impact of the proposed changes, the to-be process is simulated with the same resource-queue mechanics as the as-is log, so the before/after comparison above is a measured result, not an assumption.

## Key findings

Full detail in [`ba-artifacts/pain_point_analysis.md`](ba-artifacts/pain_point_analysis.md). Summary:

1. **Injury claims are the weak point on every metric** — worst FCR (59.8%), worst rework rate (38.4%), longest cycle time (20.97 days), driven by dependency on third-party medical records.
2. **The documentation rework loop** (16.4% of all claims) is the second-largest driver, concentrated in Property and Injury claims.
3. **Manager review is real but narrower than assumed** — only 9.6% of claims trigger it, and the problem is a periodic-load tail, not average-case slowness.
4. **Channel has a real, modest, consistent effect** — Phone/Agent submissions run 0.7–1.3 days faster than Web/Mobile across every claim type, driven by same-day vs. queued registration.
5. **What's not a pain point, stated explicitly:** inspector capacity (median queue wait 0 days) and the denial rate (an underwriting outcome, not a process defect).

## The redesign

Five changes, each traced to one of the findings above — see [`ba-artifacts/to_be_process_map.md`](ba-artifacts/to_be_process_map.md) for the full diagram and mechanism:

| Change | Targets |
|---|---|
| Same-day registration on every channel | Channel-driven delay |
| Document completeness check at intake | Documentation rework loop |
| Medical records requested in parallel with adjuster review (fork/join), not after it | Injury's dominant cycle-time driver |
| Widened, configurable fast-track eligibility | Overall cycle time, especially Property |
| Small overflow reviewer pool, threshold-triggered | Manager-review p90 tail, without added permanent headcount |

## Reproducing this analysis

```bash
pip install numpy pandas duckdb --break-system-packages   # or use a venv
python data/generate_claims_log.py                        # as-is log
python data/generate_claims_log_tobe.py                    # to-be log
python analysis/analysis_cycle_time.py
python analysis/analysis_rework_fcr_segments.py
```

Both generators are seeded (`RNG_SEED = 42`) for reproducibility — a fresh run reproduces the exact numbers cited throughout this repo.

## Tech stack

Python (numpy, pandas) for the event-log simulation · DuckDB for SQL aggregation directly over CSV, no server/load step · Mermaid for version-controlled process diagrams · Power BI (in progress) for the operations dashboard.
